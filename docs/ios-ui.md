# keyref iOS 界面规格

状态：v0.2。本文是 docs/design.md §12.1 在界面层的展开：信息架构、逐屏规格、关键交互决定。不是实现记录，也不重定义协议——只引用 §编号。

日期：2026-10-27（v0.2 按当日实际代码核对交付状态；初版 2026-10-24）。

**v0.1 的 Phase 1 三条边界，逐条交付状态（对照 ios/README.md 与 KeyrefUI 代码）：**

1. **审批界面：已交付。** 审批收件箱（命令原文含 `--allow-argv` / `--reply` 模式、条目名称、发起设备、倒计时，批准需 Face ID，§8.3）在 KeyrefUI（ApprovalsStore.swift、ApprovalViews.swift）；审计详情已显示「审批结果：已批准 / 已拒绝」（AuditViews.swift）。审批详情同时展示执行上下文（可执行文件、实际执行文件、解释器链、工作目录，协议 §6.19）。到达方式当前是前台轮询——APNs 推送仍待 Apple 开发者凭据（见第 5 节）。
2. **「旧手机扫新手机」配对：已交付。** 第二台 iPhone 在线配对落地（SecondDeviceFlowModel.swift、KeyrefCore/SecondDevice/OwnerPairing.swift），不再只有恢复码接管一条路；恢复码接管（§8.5、§9.4）仍是兜底。
3. **Plus 内购入口：仍然没有。** 内购需要 Apple 开发者凭据，另行接入（ios/README.md）。内购上线前托管只有免费档（§10.5），超额页只给出路（删除、自托管），不给升级按钮。

另注：条目编辑的敏感级别仍固定「标准」、不提供 approval 档位（ItemViews.swift 策略区注释与 §2.6 一致）；`allowCommands` / `allowedHosts` 的精细编辑（命令搜索、覆盖默认拒绝的红色警示卡）已交付，§2.6 相应更新。自协议 v2 H 起，「拒绝 shell 与解释器」开关（`commandPolicy`）真正被 CLI 读取：已配对库上关掉它（`allow-all`）是不为条目设置 `allowCommands` 的唯一方式；approval 档位与存储类别仍是同一个轴，拆成两轴需要改界面（design §15 的开放问题）。

文案约定：界面与本地通知文案一律简体中文；代码标识保持英文——`ref`、`VMK`、`Face ID`、`allowArgv`、`{{keyref:openai-prod}}`。服务器错误码（`quota_exceeded` 等）原样展示并配一句中文解释。CLI 的机器可读输出是英文，那是 §12.2 的规定，不在本文件范围。文中「文案」栏给出的字符串就是最终文案，不是占位句。

## 1. 信息架构

### 1.1 四个 Tab

| Tab | 内容 | 理由 |
| --- | --- | --- |
| 条目 | 列表、详情、编辑、新建；引导流程覆盖其上 | 产品的主要内容。空库时的引导创建也挂在这里，因为它的终点就是这张列表 |
| 设备 | 设备列表、扫码配对、设备详情、授权管理、撤销 | 配对、追加/收回授权、撤销是这台应用里最锋利的一组操作。独立成 Tab，和日常翻看条目的路径分开，避免「顺手点进危险区」 |
| 审计 | 本机解密的事件流、事件详情、筛选 | 「每一次 exec 都有审计记录」是 §2.1 的产品承诺，审计是信任证据，不是附属功能，值得一级入口 |
| 设置 | 服务器 origin、档位与用量、安全、恢复、危险区 | §12.1 要求人始终能知道密文送到了哪里。origin 是一级信息，不该藏在列表左上角的齿轮里 |

**取舍：**

- 审计不并入设备（做成「每台设备的活动」）：审计事件跨设备，人的第一问是「最近发生了什么」，按设备过滤只是二级细化。设备维度作为筛选器放在审计 Tab 内。
- 设置不做成条目列表的工具栏齿轮：keyref 的设置里有三件低频但致命的事——改服务器、删库、恢复码。独立 Tab 让「服务器归属」长期可见，也让危险区有一个稳定的、不会被误触的位置。
- 审批收件箱不新增第五个 Tab：审批是即时任务（60 秒包裹、2 分钟超时，§8.3），靠条目 Tab 顶部的徽标横幅到达（当前为前台轮询；APNs 推送待 Apple 开发者凭据接入后加入），不能指望人主动巡检一个常空的板块。

### 1.2 导航层级

```text
Tab 1 条目
  ├─ 引导流程（未创建保险库时全屏覆盖）
  │    ├─ 欢迎页（创建 / 恢复码恢复 两条入口）
  │    └─ 创建保险库：前置检查 → 生成 → 恢复码展示 → 抄写回填 → 完成
  ├─ 条目列表（搜索、同步状态点、超额/冻结横幅）
  │    ├─ 新建条目
  │    └─ 条目详情（查看明文、替换值=轮换、删除）
  │         └─ 编辑条目（含策略编辑）
  └─ 同步失败详情（横幅进入）
Tab 2 设备
  ├─ 设备列表（本机置顶；已撤销折叠）
  │    ├─ 扫码配对（全屏相机）→ 核对页 → 条目勾选 → 完成
  │    ├─ 设备详情（CLI）：授权清单（追加/收回）、备注、撤销入口
  │    │    └─ 撤销设备（专用页：轮换选择 + B6 → 进度 → 完成）
  │    └─ 设备详情（本机）：隔区状态、自动锁定入口
Tab 3 审计
  └─ 审计流 → 事件详情（筛选：设备 / ref / 结果）
Tab 4 设置
  ├─ 服务器 origin → 修改确认 → 迁移进度
  ├─ 保险库与配额 → 超额 / 冻结详情
  ├─ 安全（自动锁定、Face ID 说明、轮换 VMK 与恢复码、怀疑恢复码泄露）
  ├─ 恢复（输入恢复码 → 接管 或 本机重建 → 进度 → 完成 → 重新配对指引）
  └─ 危险区（删除保险库，两步）
```

深度原则：任何破坏性操作的终点距离 Tab 根不超过 2 层 push；超过两层的信息（审计详情、事件参数）只读不写。

### 2.1 欢迎页（未创建保险库，S1）

- **用途**：创建或恢复的唯一起点。保险库存在后此页不再出现。
- **入口/出口**：首次启动、删除保险库完成后（2.16）自动到达。出口只有两个按钮。
- **核心元素与文案**：
  - 标题「keyref」
  - 副标题「你的秘密保险库。agent 只拿引用，拿不到明文。」
  - 主按钮「创建保险库」→ 2.2
  - 次按钮「用恢复码恢复」→ 2.12
  - 底注「主密钥只活在这台手机的安全隔区里。服务器只保存密文。没有账号，也没有客服重置。」

### 2.2 创建保险库

- **用途**：§12.1 流程 1、§9.3。生成隔区密钥与 VMK、展示恢复码（只显示一次）、校验抄写、上传。
- **入口/出口**：欢迎页主按钮。完成后进入条目列表；中途退出则本地数据保留、可从欢迎页重新进入（恢复码若已展示，仍以本机保存的为准继续上传）。
- **步骤条**：前置检查 → 生成密钥 → 抄写恢复码 → 校验抄写 → 完成。

**前置检查**：设备密码已设置、Face ID 已录入（`.biometryCurrentSet` 的隔区密钥两者缺一不可，§9.3）。缺哪项给哪项的系统设置深链，文案「先在系统设置里开启设备密码 / Face ID，再回来创建。」

**生成页**：逐行列出要创建的东西——安全隔区协定密钥与签名密钥、主密钥 VMK、恢复码、续期密钥对（§8.4）。按钮「创建」。系统会在生成隔区密钥时自行要求认证，应用不再叠加自绘确认。

**恢复码展示页（S9）**：

- 标题「抄下恢复码」
- 正文「这是它唯一一次出现。恢复码等于全部数据：keyref 不保存它，设置里也没有再次查看的入口。抄在纸上，或放进另一个你信任的保险库。」
- 警示条「手机和恢复码同时丢失＝数据永久丢失。」（§9.5 要求创建确认页写明这句话）
- 恢复码本体：Crockford Base32 分组，大号等宽字体，每组一个框。**故意不提供拷贝按钮**（理由见 3.4——恢复码进剪贴板等于进 Universal Clipboard）。
- 按钮「我已抄写，开始校验」。

**校验抄写页（分组回填）**：

- 交互：按顺序重输全部分组。自动聚焦、写满一组自动跳下一组；支持整段粘贴（自动去掉空格与连字符、按组拆分）；Crockford 归一化（0/O、1/I/L 视为同字符）。填错的组实时标红，正确后变绿。
- 全部匹配：成功触感 + 进入完成页。不匹配：错误组标红，光标停在该组，文案「有一组和屏幕上的不一致，请对照你抄写的那份修改。」
- **为什么全量回填而不是抽查 3 组**：回填校验的对象是「你抄下来的那份副本」，不是「你是否动手抄了」。抽查只能证明 3 组对；抄错一位等于将来恢复必败，代价不对称。全量回填约 40 秒，一次性成本。它防不了拍照——它不防「没抄」，只防「抄错」，这句话写进本规格，也写进该页脚注。

**完成页**：

- 标题「保险库已创建」+ 同步状态（上传中 / 已同步）。
- 底注（逐字）「恢复码是唯一的恢复方式。keyref 无法帮你重置。」
- 按钮「进入保险库」。

**错误态**：上传失败（网络、`rate_limited`、工作量证明失败）→「保险库已在本机创建，但还没同步到服务器。」+「重试上传」。重试不重新生成恢复码。**加载态**：生成步骤的进度行（「正在生成安全隔区密钥…」），密钥生成本身不显示百分比。

### 2.3 解锁锁定屏（S2、S3、S4）

- **用途**：VMK 不在内存时的全屏遮罩。进前台即出现（§9.5：默认进后台 1 分钟即锁定，间隔可设置）。同时是两种解锁失败的载体——这两种失败面必须长得不一样。
- **入口/出口**：进前台、手动锁定。出口：Face ID 成功。
- **正常态（S2）**：
  - 标题「keyref 已锁定」
  - 状态行「N 条条目已就绪」（计数是缓存的非敏感数字）
  - 主按钮「使用 Face ID 解锁」→ 发起 `LocalAuthentication`（理由见 3.1：系统弹窗之上必须垫一层自绘遮罩，因为系统弹窗可以被取消）
  - 底注「解锁只发生在这台手机上。」
- **失败态一：Face ID 失败（S3）**——包裹完好，重试即可：
  - 错误行「Face ID 没有识别成功，再试一次即可。」
  - 连续多次失败后追加「先解锁手机，正对摄像头再回到 keyref。」
  - **没有「用设备密码解锁保险库」按钮**。`.biometryCurrentSet` 下设备密码解不开隔区私钥（§9.2），放假按钮是撒谎；口令降级只存在于 §9.2 的退路架构里，启用退路必须显式改文档。
- **失败态二：本机包裹已失效（S4）**——重录 Face ID / 增删指纹 / 关闭再开启设备密码导致隔区私钥永久失效（§9.5），解锁在密码学上不可能：
  - 标题「本机包裹已失效」
  - 正文「重录 Face ID、增删指纹或更改设备密码后，原来的加密包裹会永久作废——这是「新的生物特征集合不再被信任」的定义，不是故障。你的数据还在本机，没有被读取或删除。」
  - 主按钮「用恢复码在本机重建」→ 2.13
  - 链接「了解发生了什么」→ 安全说明页
  - 这一面没有「再试一次」按钮——区分两种失败面的意义就在这里：一个是摩擦，一个是结局，混在一起会让人对着死锁狂按重试。

### 2.4 条目列表（S5、S6）

- **用途**：§12.1 流程 2。解锁后的主界面。
- **入口/出口**：Tab 1 根。行点击 → 条目详情（2.5）。
- **核心元素**：
  - 行：名称（主文字）、`ref` 与掩码（次要色、等宽字体，如 `openai-prod · sk-****abcd`）、类型徽标（KEY / TOKEN / 密码 / 笔记 / 通用）。按更新时间倒序，不分组（免费档 20 条，分组是负资产）。
  - 工具栏：搜索（本地匹配名称/`ref`/描述——服务器没有搜索，§2.2；锁定时列表不存在，所以搜索天然只在解锁后可用）、添加按钮。
  - 同步指示：工具栏圆点三态——同步中 / 离线 / 失败。点按进失败详情。
- **空态（S5）**：「还没有条目」/「添加第一条密钥，配对时再把它授予 agent。」按钮「添加条目」。
- **加载态**：无骨架屏。解锁后立即渲染本地密文的解密结果，同步异步进行——本地存的就是全量密文，首屏不需要等网络。
- **同步失败（S6）**：列表顶部横幅「同步失败——你的修改已保存在本机，恢复网络后自动重试。」点开显示最近一次错误与时间。错误码到文案的映射：

| 错误码 / 情形 | 展示文案 |
| --- | --- |
| 网络不可达 | 「连不上服务器，稍后自动重试。」 |
| `rate_limited` | 「请求太快被限流，稍后自动重试。」 |
| `quota_exceeded` | 「免费额度已用尽。」+ 超额页入口（2.17） |
| `device_revoked` | 「这台设备已被撤销。」+ 恢复码接管入口（2.12）——接管自另一台手机后，旧手机会走到这里 |
| `cursor_stale` | 静默重置游标重新引导（§10.6），不打扰用户 |
| 签名 / revision 校验失败 | 「服务器返回的数据没有通过校验，已拒绝应用。」不自动重试，等下一次手动刷新（§10.6：验证失败就停止应用这一批） |

### 2.5 条目详情

- **用途**：查看元数据、查看明文、轮换、删除。也是授权的反向视图。
- **入口/出口**：列表行。出口：编辑（2.6）、删除、返回。
- **核心元素**：名称、`ref`（可拷贝——`ref` 不是秘密，agent 要靠它写命令）、描述、类型、掩码、策略摘要行（敏感级别：标准 / 拒绝 shell：开 / 参数检查：N 个主机 / 进程参数注入：关）、创建与修改时间。
- **「已授权设备」区**：每行 = 设备名 + 授权级别（查看 / 使用）+ 到期日。S14 标记：7 天内到期加黄色「7 天后到期」，1 天内红色「明天到期」。空态「还没有设备被授予这条条目。」
- **查看明文**：按钮 → Face ID（每次点开都要，包括本会话刚看过同一条——规则要简单到可预见，宽限窗口反而帮到「拿起别人未锁手机随手翻看」的场景）→ 明文层：显示/隐藏切换，30 秒无操作自动收起（肩窥面；不打断 30 秒内完成的核对或抄写）。明文层内出现「拷贝」按钮（剪贴板策略见 3.4）。掩码的 VoiceOver 读法见 3.6。
- **替换值（轮换）**：sheet：新值输入框（不回显旧值）→ 确认行「保存后将生成新的条目密钥，重新加密并重新下发给所有已授权设备（N 台）。」→ Face ID → 成功 toast「已轮换并同步」。`ref`、名称、策略不动。
- **删除**：confirmationDialog，destructive 红色（确认模式分档见 3.3）：「删除 openai-prod？」副文「agent 对它的引用会立刻失效，同步后不可撤销。」红色「删除」→ Face ID。

### 2.6 新建 / 编辑条目（含策略编辑）

- **用途**：§12.1 流程 3 的编辑面。策略的**精细编辑**（§13 的 Phase 2 项：allowCommands/allowedHosts 列表增删 + 命令搜索 + 覆盖默认拒绝的红色警示卡）已交付。
- **入口/出口**：列表添加按钮 / 详情「编辑」。出口：保存（Face ID 签名上传）、取消。
- **字段**：
  - 名称、描述：文本框。
  - `ref`：仅新建可填，行内校验语法（`^[a-z][a-z0-9-]{0,62}[a-z0-9]$` 或单字符，§6.1）与唯一性（冲突时「这个 ref 已被「OpenAI 生产密钥」使用」）。编辑页只读展示，脚注「ref 是脚本和对话里的稳定引用，创建后不可改名。」
  - 类型：仅新建可选（api_key / token / password / note / generic）。
  - 值：编辑时可留空 = 不修改。
- **策略区（Phase 1 基础编辑）**：
  - 敏感级别：当前固定显示「标准——配对并授权后可无人值守使用」，**不提供 approval 档位**（ItemViews.swift 策略区注释同此）。审批机制本身已交付（§8.3、CLI `--reply`），但 `sensitivity=approval` 的条目目前不经本界面产生；meta 格式从第一天就保留 `sensitivity` 字段（Phase 0 格式要求），UI 开放档位见第 5 节。
  - 「拒绝 shell 与解释器」开关（`deny-shells`），默认开。脚注「阻止 agent 用 sh、bash、python、node 等解释器接触这条秘密。关闭后任何命令都能拿到它。」
  - 命令白名单（`allowCommands`）：列表增删 + 「搜索命令」建议（精细编辑已交付，ItemViews.swift）。**放行的名字命中默认拒绝名单时**出现红色警示卡——标题「白名单覆盖了默认拒绝名单」，正文「已放行 <命中的命令>——解释器一旦放行，模型可以把秘密切片打印，输出脱敏器会失明。建议把这类条目的敏感级别设为 approval，让每次执行都过一遍 Face ID（§7.3）。」保存时再确认一次；脚注「白名单非空时它就是全部：argv0 必须命中其中一项。名单可以覆盖默认拒绝——保存时会再向你确认一次。」
  - 参数检查（`allowedHosts`）：区块标题就叫「参数检查」，**不叫「网络隔离」**（§7.3 明文要求）。脚注「只检查命令参数里出现的 http(s) 主机名，必须与列表完全一致。重定向、IP 直连、程序内拼出的 URL 都查不到——这不是网络隔离。」
  - 「允许放进进程参数（`--allow-argv`）」开关：打开时弹警报（§6.1 原句）——标题「进程参数对本机所有用户可见」，正文「打开后，秘密可以出现在命令行参数里。同一台机器上的任何用户都能通过进程列表（ps、活动监视器）看到。CLI 侧还必须显式加 --allow-argv，两边都打开才生效。」按钮「允许」/「不允许」。
  - note 类型追加：「允许注入命令」开关，默认关（`injectable`，§6.1），脚注「笔记默认不注入命令。打开后 CLI 才能把它的值放进环境变量或文件描述符。」
- **保存时的粘贴检查（§12.1 流程 3）**：名称与描述和条目值及常见编码比对（与 §7.4 同一套匹配器：原文、Base64、hex、percent-encoding）。命中 → 警报：标题「名称里出现了这条秘密」，正文「名称与描述会进入 agent 的上下文，agent 能直接读到。检测到与条目值或其 Base64 / hex / URL 编码一致。」按钮「回去修改」/「我知道，仍然保存」。**可强制保存**：这道检查挡的是手滑，不是审查，最终决定留给人。
- **错误态**：超额状态下保存被 `quota_exceeded` 拒绝 →「免费额度已用尽，不能新增或修改。仍可查看和删除。」（S12 关联）。

### 2.8 扫码配对（S7、S10、S11）

- **用途**：§12.1 流程 4、§8.1。方向是**手机扫终端**（CLI 没有摄像头）。
- **入口/出口**：设备列表。出口：完成页 / 取消。
- **取景页**：全屏相机 + 取景框 + 手电筒按钮。未识别到有效码时（S7）：
  - 主文案「在 agent 的机器上运行 keyref pair」
  - 副文案「把终端上出现的二维码对准取景框。配对码 10 分钟内有效。」
  - 警示行「只扫你面前这台机器屏幕上的码——旁边的屏幕可能属于别人。」（§8.1：避免扫到旁边屏幕的二维码）
- **相机权限被拒的降级路径**：整页替换为「相机权限已关闭」/「配对码只能用相机扫描，keyref 不提供手动输入的替代路径。到系统设置里打开相机权限，回来继续。」按钮「打开设置」（系统设置深链）。不做相册识码、不做手动输入，理由见 3.2。
- **核对页**（扫到有效码后）：
  - 设备名（CLI 自报，可后改，§6.4）
  - 指纹：`A1B2-C3D4-E5F6-7890` 格式，大号等宽 + 指令行「与终端上印出的指纹逐组核对」。指纹核对只能靠人对屏，这正是 A7 的防线，界面把它做成最显眼的元素而不是脚注。
  - origin 行（S10）：「同步服务器：https://keys.example.com」，旁标手机当前 origin。
  - **origin 不一致（S11）**：红色警示卡——标题「配对码指向另一台服务器」，正文「终端连接的是 keys.example.com，你的手机当前同步到 sync.example。继续配对会把手机切换到 keys.example.com：密文与授权关系将同步到那台服务器。加密强度不变，但你要确认自己信任它的运营者。」按钮「切换并继续」/「取消」。**切换前先探测**：新 origin 上不存在本 `vault_id`（用未登录的 recovery 端点探测，§8.5）时，主按钮变为「先迁移服务器」深链 2.15——手机已有保险库而目标服务器上没有，直接切过去只会得到一个空库。
  - 按钮「继续」→ 勾选页。
- **勾选页**：全部条目**默认不勾选**（§15：配对完成时授予集合为空）。行 = 名称 + `ref` + 掩码。脚注「勾选的条目将被授予查看与使用权限，默认 30 天有效、自动续期。现在什么都没有授予——勾选并确认之后才算。」主按钮「用 Face ID 确认（N 条）」（N=0 时禁用并显示「至少勾选一条，或直接取消配对」）。
- **完成页**：「配对完成」/「终端会显示成功，并拿到你勾选的条目。」链接「管理这台设备的授权」→ 2.9。
- **错误态**：码过期「配对码已过期。在终端重新运行 keyref pair，再扫一次。」；nonce 已消费「这个配对码已被使用。」；网络/服务器错误「配对没有完成，没有授予任何条目。请重试。」

### 2.9 设备详情（CLI）与授权管理

- **用途**：§12.1 流程 5 的日常面——按设备管理授权（对应 `PUT` / `DELETE /v1/grants`）。
- **入口/出口**：设备列表。出口：追加授权、收回、撤销（2.10）。
- **核心元素**：名字（行内改备注，§6.4 允许 owner 改 label）、状态、指纹、添加时间、「最近活动」——本机审计流按此设备过滤的前 5 条 + 「查看全部」（深链审计 Tab 并带上筛选）。
- **授权清单区**：每行 = 条目名 + `ref` + 级别（查看 / 使用）+ 到期日 + S14 标记。区脚注「到期前会自动续期：每次打开 keyref 解锁时顺延即将到期的授权（§8.4）。」
- **收回单条**：左滑 → confirmationDialog：「收回「openai-prod」的使用授权？」红色「收回」，副文「设备下次同步后失效。已经拷到那台机器上的密钥不受影响——必要时撤销整台设备并轮换（B6）。」
- **追加授权**：sheet 列出尚未授予的条目（默认全不选）→「授予（N 条）」→ Face ID → 完成。
- **撤销入口**：页面底部红字「撤销这台设备」→ 2.10。

### 2.10 撤销设备（专用页，含 B6）

- **用途**：§8.4 默认动作：签新目录 → 删 grants → **轮换**该设备曾持有使用授权的条目密钥。
- **入口/出口**：设备详情。出口：完成页 / 取消。
- **第一步（专用页，不是弹窗——理由见 3.3）**：
  - 标题「撤销 {设备名}」
  - 摘要行：指纹、授权 N 条，其中 M 条有使用授权。
  - 默认勾选的选项：「同时轮换这 M 条条目的密钥」（默认**勾选**）。其下的解释就是 B6 的产品文案——「撤销只能拦住服务器这条路。那台机器上已经解开的密钥副本，在轮换之前仍然有效——哪怕它被改得不再理会过期时间。轮换会生成新密钥、重新加密这 M 条条目，并把新密钥发给其余设备。」
  - 次级链接「不轮换，仅停用」→ 二次警报：「仅当确认密钥从未离开那台机器时才安全。适用于设备退役；如果只是怀疑它出了问题，请保持轮换。」按钮「仅停用」（destructive）/「返回，保持轮换」（§8.4：只撤销不轮换放在二级确认后面）。
  - 主按钮「撤销并轮换 M 条」（红色）→ Face ID。
- **第二步（进度页）**：三项清单逐项打勾——重签设备目录、删除授权、重新加密 M 条。完成页「已撤销」/「那台设备下次联网同步时会收到停用指令。」
- **失败态**：轮换中途中断（网络断开）→ 页面保持「撤销已生效，轮换还剩 K 条」+「继续轮换」。目录签名与授权删除先落库（撤销本身不可回退），轮换作为可恢复任务继续。design.md 未定义中断语义，这是本规格补的最小方案：撤销先于轮换生效，轮换可重入。

### 2.11 审计列表与事件详情

- **用途**：§12.1 流程 7。审计正文加密给 owner，**本机解密**（§7.7）；服务器只见密文。
- **入口/出口**：Tab 3 根。行 → 事件详情。可从设备详情带筛选深链进入。
- **解密行为**：进入 Tab 时若隔区要求认证，一次 Face ID 解一批（§7.7：每个事件随机事件密钥、分别 HPKE 给每台 owner，本机只解发给自己的）。不给「网络解密」的错觉——解不开就显示失败，不显示占位内容冒充数据。
- **列表行**：时间、设备名、`ref` 列表（多个截断）、结果徽标（策略通过 / 被拒绝 / 退出码 N）、脱敏替换次数。筛选器：设备、结果（通过/拒绝）、`ref`。
- **事件详情**：完整 argv（占位符形式、等宽字体）、注入方式（env / fd / stdin / argv）、策略结果、退出码、脱敏替换次数、时间与设备。脚注「argv 显示的是占位符形式，keyref 不会记录替换后的秘密。」审批结果字段位显示「已批准 / 已拒绝」（已交付，AuditViews.swift）。
- **保留期脚注**：「免费档保留 7 天、最多 100 条，到期由服务器删除。」（§7.7、§10.5）
- **空态**：「还没有审计记录」/「agent 第一次用 keyref exec 之后，每一次尝试——包括被拒绝的——都会出现在这里。」
- **失败态**：单条解密失败 → 该行显示「一条无法解密的记录」，不阻塞列表；整批失败 → 「审计解密失败，下拉重试。」
- **VoiceOver**：argv 中的 `{{keyref:openai-prod}}` 读作「占位符 openai-prod」，不逐字符朗读花括号。

### 2.12 恢复码接管流程

- **用途**：§12.1 流程 8、§8.5。新手机接管、或主动迁移时用。第二台 iPhone 现在也可在线配对（2.7/2.8）；需要把旧设备全部撤销时，接管就是迁移。
- **入口/出口**：欢迎页「用恢复码恢复」；设置 → 恢复；`device_revoked` 状态页（2.4）。出口：完成页 → 重新配对指引 → 扫码配对。
- **说明页**：标题「用恢复码接管保险库」，正文「输入恢复码后，这台手机会解开主密钥、成为唯一的 owner 设备，并把之前登记的所有设备——包括丢失的那台 iPhone 和全部 CLI——标记为撤销。如果旧手机还在手上且能正常解锁，加一台新 iPhone 也可以走在线配对（2.8），那里不撤销任何设备；选择接管就是选择迁移。」按钮「输入恢复码」。
- **输入页**：与 2.2 回填同一套分组输入控件（粘贴自动归一）。错误态：
  - 「恢复码不正确。」（AEAD tag 校验失败，§8.5：tag 就是判据）
  - 「在当前服务器上找不到这个保险库。」正文「恢复码自带保险库地址。如果你是自托管，先在设置 → 服务器里改到你的 origin，再回来输入。」（`vault_id` 在码里、服务器可配置，指向错误 origin 是真实高频错误）
  - 限流：「尝试太频繁，请稍后再试。」
- **进度页**：清单逐项——取回恢复材料 → 解开主密钥 → 生成这台手机的新隔区密钥 → 签署接管誊本 → 下载全部密文 → 轮换条目密钥并重加密。第 4 步前有确认警报：「提交后，之前的所有设备立即失去同步，CLI 需要重新配对。」按钮「提交接管」/「取消」。最后一步是自动执行的后台任务（丢失的 iPhone 是 owner，持有过 VMK，按 §8.4 默认动作轮换），完成后无需人工确认。
- **完成页**：「保险库已恢复」+ 摘要「N 条条目、M 台设备已被撤销」。底注（§9.5 要求恢复完成页写明）「恢复码没有变化，仍然是唯一的恢复凭证。手机和恢复码同时丢失＝数据无法恢复。」按钮「重新配对 CLI」。
- **重新配对指引页**：三步说明——「1. 在每台 agent 机器上重新运行 keyref pair。2. 用这台手机扫终端上的二维码。3. 重新勾选要授予的条目——旧授权不会自动恢复。」按钮「扫码配对」→ 2.8。
- **失败态**：任一步网络失败可在该步重试；提交接管成功后失败（下载中断）→「接管已生效，密文还在下载。重进后从断点继续。」接管提交是不可回退点，页面文案要区分「生效前可取消」与「生效后只能继续」。

### 2.13 本机包裹失效重建流程

- **用途**：§9.5 的第二半：`.biometryCurrentSet` 变化后，在同一台手机上重解 VMK、在新隔区重新包裹。**不是**新手机接管。
- **入口/出口**：锁定屏 S4 的按钮。出口：完成 → 解锁后的列表。
- **与 2.12 的三处差异**（共用同一套屏幕骨架，只换文案与步骤）：
  - 说明页：「输入恢复码，在这台手机上重新包裹主密钥。其他设备不受影响，CLI 不需要重新配对。」
  - 进度第 4 步是「更新本机在设备目录中的登记」（接管誊本只改本机那一行，§8.5），没有「撤销全部旧设备」的确认警报；本地密文尚在，第 5 步显示「校验本地密文」而非全量下载。
  - 没有重新配对指引页；没有条目轮换步骤——生物特征集合变更不是泄露事件。
- **完成页**：「本机已恢复」+ 同一句底注「恢复码没有变化，仍然是唯一的恢复凭证。手机和恢复码同时丢失＝数据无法恢复。」

### 2.14 设置

- **用途**：低频但关键的控制面。§12.1 流程 9 的入口。
- **入口/出口**：Tab 4 根。
- **分区**：
  1. **服务器**：origin 行 + 归属徽标（S10，两套文案）——官方托管「官方托管 · 只保存密文，受免费档配额约束」；自托管「自托管 · 密文送到你指定的服务器，端到端加密不变」。点按 → 2.15。数据来自 `POST /v1/session` 响应里的 `origin` 与 `plan`（§11），不靠客户端猜。
  2. **保险库与配额**：档位行与用量（条目 12/20、存储 0.4/1 MB、今日请求 87/500）→ 2.17。Plus 行 Phase 1 灰置：「Plus（$6/月）随内购上线。」
  3. **安全**：自动锁定（立即 / 1 分钟 / 5 分钟，默认 1 分钟，§9.5）；Face ID 说明行（点开：「重录面容、增删指纹或更改设备密码会使本机包裹失效，需要用恢复码重建。」）；「轮换 VMK 与恢复码」→ 确认页「怀疑主密钥材料暴露、但条目没有泄露时使用。只换包裹层，条目密文不动。」→ 生成新 VMK、重新包裹、**展示新恢复码（复用 2.2 的展示与回填，S9）**；「怀疑恢复码泄露」→ 确认页「新恢复码 + 轮换全部条目密钥并重加密。旧恢复码的持有者从此解不开任何新密文。条目较多时需要几分钟。」（B5 的处理，§8.4；重加密复用撤销轮换的同一代码路径）
  4. **恢复**：「用恢复码接管」→ 2.12。固定说明行（任务要求的显式声明）——「恢复码不能再次查看。keyref 不保存它，没有任何入口能重新显示。忘了、又没抄下来，数据无法恢复。」
  5. **危险区**：「删除保险库」→ 2.16。
  6. 关于：版本、协议版本。

### 2.15 服务器 origin 修改与迁移

- **用途**：§12.1「改地址要先显示 origin 再确认」；§8.5 的迁移路径。
- **入口/出口**：设置 → 服务器。出口：迁移完成 → 设置。
- **修改页**：当前 origin、新 origin 输入框。归属实时预览（输入官方域名 → 「官方托管」徽标，否则「自托管」）。正式构建拒绝 `http://` 与自签证书（§10.4），行内错误「正式版只接受系统信任的 HTTPS。」
- **确认页**（保险库已有数据时）：标题「切换服务器」，三条后果逐条列出——「新服务器上会重建这个保险库，并上传全部密文。」「所有 CLI 设备要改指向新地址并重新配对。」「旧服务器上的副本不会被自动删除。要清理时，把服务器改回旧地址执行删除。」按钮「切换」→ Face ID → 迁移进度页（在新 origin 创建 → 全量上传 → 校验）→ 完成页「已迁移到 keys.example.com」+「下一步：在每台 CLI 上运行 keyref server set <新 origin>，再重新 keyref pair。」
- **空库**（未创建保险库）：直接改，无确认页。

### 2.16 删除保险库（两步）

- **用途**：§12.1 流程 9、§11 的两步协议（先领挑战，再签名确认）。全应用影响半径最大的操作，配最重的确认（3.3 第三档）。
- **入口/出口**：设置 → 危险区。出口：完成 → 欢迎页（S1）。
- **第一页**：标题「删除整个保险库」，后果清单——「服务器上全部密文、设备与授权记录立即级联清空。」「所有 agent 的引用立即失效。」「恢复码随之作废。」「本机缓存在删除应用时清掉。」输入框：手动输入「删除」两个字（不可粘贴）→ Face ID → 签名提交。
- **第二页**：进度 → 完成「保险库已删除」→ 欢迎页。
- **失败态**：请求未完成 →「删除没有完成，数据还在。请重试。」**绝不显示「已删除」，除非服务器确认成功**——误报比慢更危险。

### 2.17 超额与冻结状态页（S12、S13）

- **用途**：§10.5 超额允许操作集合与冻结语义的界面化。状态来自 `GET /v1/account` 与写入时的错误码。
- **超额（S12）**：各 Tab 顶部横幅「免费额度已用尽 · 仍可查看与删除」+ 详情页：
  - 标题「免费额度已用尽」
  - 原因行：哪项触顶（条目数 / 存储 / 今日请求数），显示当前用量与上限。
  - 「现在仍然可以」清单：查看全部条目、撤销设备、收回授权、删除条目、删除保险库。
  - 「现在不能」清单：新增或修改条目、配对新设备。
  - 出路：「删除条目，降回限额内」（深链列表，按密文大小排序——本地有密文，长度可知）；「改用自托管服务器」（→ 2.15）；Plus 行灰置「随内购上线」。**没有升级按钮**，Phase 1 不撒谎。
- **冻结（S13）**：横幅「保险库已冻结」+ 页面：「免费档连续 180 天没有设备成功登录，保险库转为只读。数据没有被删除。刚才的登录已触发解冻，现在可以正常使用。」解冻是自动的（任何一次成功登录即解冻，§10.5），页面职责是把发生的事说清楚，而不是提供解冻按钮。
- 两页在超额/冻结期间常驻可从横幅与设置进入；解除后横幅消失，页面不再可达。

### 2.18 短信收件箱与短信审批（v0.8 §14.4、§14.5）

- **入口**：设备 Tab 首节，「收件箱」一行（与「待审批」并列，右侧显示当前条数）。不放第五个 Tab——§1.1 的四 Tab 契约不变。
- **收件箱**：按来源设备 label 分组（分组标题即 label），组内按服务器 `created_at` 倒序。每行：发信号码、正文（最多三行）、到达时刻（`HH:mm`）、剩余有效期（剩不到一小时转警告色）。单条左滑删除；工具栏「清空」带一次确认。空态：「没有新的验证码」+ 一句话说明 24 小时销毁与一次性消费。
- **详情页**：完整正文（可选中复制给人自己用）、来源设备、到达时间、剩余有效期、SIM；右上角删除。底注写明「发信号码可以伪造，它只是参考信号」。
- **短信审批**：审批收件箱里 message subject 的行显示「验证码 · 发信号码」与正文摘要；详情页把短信全文、发信号码、来源设备、短信到达时间与命令原文同屏并列——人确认的是「这次登录该用哪条短信」。批准同样走 Face ID，载荷是短信明文，用掉一次该消息即置 `consumed`。
- **主接收端**：本机详情页「短信接收」一节提供「设为主接收端 / 取消主接收端」，带说明（每个保险库至多一台；验证码与审批推送指向它，无令牌时退回全部 owner 设备）。设备列表里带该角色的行显示「主接收端」标记。改动随设备目录重签（revision+1）下发，服务器只递送目录、不解释角色。
- **离线/无推送**：自托管默认没有 APNs，收件箱降级为「打开应用才看到」，与审批一致（§8.3）。设备页与收件箱打开时各拉一次。

### 2.19 自动审批委托（v0.8 §14.8）

- **入口**：设置 → 「自动审批」一节的一行「自动审批委托」，状态写「未开启 / 已开启」，副行是策略摘要（几个发信号码 · 最长几分钟 · 每小时/每天几次 · CLI 不限或几台）。未开启时副行为「每条短信的消费都要在手机上确认」。
- **编辑页**（顶层两处 `KeyrefNotice` 警示，不可折叠）：
  - 第一条：决策器持有有效期内全部短信的明文——它要读正文才能判断；妥协一台决策器的损失止于这批短信，碰不到条目与授权。
  - 第二条：decision API 复核是自动放行的必要步骤，**不可关闭**；结构策略命中只是必要条件，复核否决就保持待审批。
  - 字段：允许的发信号码（增删列表）、消息最大年龄、每 CLI 每小时 / 每天上限（0 = 不限）、允许的 CLI 设备（从目录里的 active CLI 勾选，全不勾 = 不限）。
  - 主按钮「保存并签署」：以 revision+1 签一份新策略并 PUT。**不做乐观更新**——服务端接受后才改页面上的状态，失败行内报错、状态保持原样。
  - 危险操作「撤回委托」：二次确认，确认文案写明「会签一份新的空策略，决策器从此批不了任何短信；它在撤回前已经拿到的短信明文，最长保留到各自到期」；撤回 = 空策略 `{"v":1}`，同样是 revision+1。
- 保存与撤回都不额外弹 Face ID：签名本身就走 owner 签名器（隔区访问控制），与目录重签、设为主接收端同一档。

## 3. 关键交互决定

### 3.1 Face ID：自绘锁定屏 + 系统弹窗，无口令降级

- 用 `LocalAuthentication` 系统弹窗做认证动作，但它底下永远垫一层自绘锁定屏。理由：LA 弹窗可被取消，取消后内容层绝不能露出来；包裹失效（S4）这种系统弹窗表达不了的状态也需要自绘层承载。
- 不提供「用设备密码解锁保险库」：`.biometryCurrentSet` 隔区密钥在密码学上不接受口令（§9.2）。放假按钮是欺骗，真降级只存在于 §9.2 的软件密钥退路里——启用退路必须显式改文档，不能静默。
- 自动锁定默认进后台 1 分钟（§9.5），设置里可调（2.14）。
- 查看明文每次都要求 Face ID（§12.1），不设会话级宽限：规则可预见比偶尔省一次认证更值钱，宽限帮的恰恰是「拿起别人未锁手机随手翻看」的场景。

### 3.2 二维码扫描：全屏相机，降级只通往系统设置

- 全屏相机 + 取景框 + 手电筒（终端屏幕反光是真实场景）。取景页常驻 S7 引导与「只扫面前这台机器」的警示（A7）。
- 相机权限被拒：整页替换为说明 + 系统设置深链。**不做相册识码、不做手动输入**。理由：扫码对象就在眼前的终端上，这两个降级路径覆盖不了任何真实场景，却各多一个攻击面（拿到截图/恶意码一样要过指纹核对）和一份测试面；降级路径的职责是让被拒的人去开权限，不是绕开相机。
- 配对码 10 分钟过期（§8.1），过期错误直接指引「重新运行 keyref pair」。

### 3.3 破坏性操作：三档确认，红字贯穿，Face ID 由系统出

| 档 | 适用 | 形式 |
| --- | --- | --- |
| 轻 | 删除单条条目、收回单条授权 | confirmationDialog，红色 destructive 角色，一句后果副文 |
| 中 | 撤销设备（含轮换选择） | 专用页：要解释 B6、要放一个默认勾选的轮换选项和一个次级「仅停用」——弹窗装不下这些 |
| 重 | 删除保险库 | 专用页 + 手输「删除」+ Face ID（两步协议，§11） |

原则：影响半径越大，确认越重；所有破坏性按钮一律 destructive 红色，不靠位置或文案粗细传达危险。凡是需要 Secure Enclave 签名的操作（解锁、配对、撤销、授权变更、删库、接管），系统会自动弹出 Face ID——UI 不再叠加自绘的二次确认弹窗，一次认证一个语义。

### 3.4 剪贴板：明文可拷贝，恢复码永远不可

- 查看明文需再次 Face ID（§12.1 明文）。「拷贝」按钮只存在于明文层——没有绕过 Face ID 的拷贝路径。
- 拷贝行为：写入**仅本机**剪贴板（不进 Universal Clipboard——同一 iCloud 账户旁的 Mac 会同步到秘密）+ 90 秒自动过期 + 成功触感 + toast「已拷贝，90 秒后自动清除」。90 秒覆盖「切到目标 App 粘贴」的动作；iOS 在目标 App 侧本就会显示「keyref 粘贴」横幅，不含秘密内容。
- **恢复码展示页（2.2）与轮换恢复码页故意没有拷贝按钮**：恢复码等价于 VMK，进剪贴板等于进 Universal Clipboard 和可能存在的剪贴板历史。同理，恢复码也不出现在任何分享 sheet 里。

### 3.5 列表掩码：只解 meta，不做批量

- 列表行只显示 meta 里的 `masked`（§6.1：掩码在保存时算好放进 meta，列表不解密 secret）。锁定时整个列表不存在——本地存储只有密文。
- 掩码等宽字体 + 次要色；`sk-****abcd` 与 `***` 的区别靠内容本身，不新增颜色语义。
- **Phase 1 不做多选批量操作**。理由：免费档 20 条、Plus 500 条的量级，单条操作够用；批量删除的主要用途（超额降回限额）由 2.17 的「按大小排序 + 单条删」覆盖；多选引入误删面，与「破坏性都要确认」的原则相抵。将来若真有批量需求（批量收回授权），它属于设备详情的勾选页，不属于条目列表。

### 3.6 Dynamic Type、深色模式、VoiceOver

- 全部跟随系统深色模式，无独立主题；掩码不引入新的颜色语义（见 3.5）。
- 动态字体：正文与表单全跟随；恢复码分组框在特大字号下横向滚动成组，不缩字号——恢复码上的字号就是防误读的一部分。
- VoiceOver：
  - 掩码读法：api_key / token 读「已隐藏，末四位 abcd」；password / note 读「已完全隐藏」。不朗读 `*` 和连字符。
  - 恢复码：提供逐组朗读模式（每组朗读后手势推进），并支持外接键盘逐组输入回填。这是已知的最薄弱无障碍路径——视觉抄写对盲人用户不成立，逐组朗读 + 键盘回填是当前能给出的最完整替代；design.md 未覆盖这一场景。
  - 审计 argv：`{{keyref:openai-prod}}` 读作「占位符 openai-prod」。
  - 指纹核对串按组朗读（「A1B2」「C3D4」…），配合人对屏核对。
- Phase 2 起应用内渲染配对二维码时，替代文本固定为「这是配对码，内容是设备公钥，不含任何秘密」。

### 3.7 触感反馈：只标记不可逆时刻与校验结果

| 时刻 | 反馈 |
| --- | --- |
| 解锁成功、回填校验通过、配对完成、接管完成 | `.success` 通知触感 |
| Face ID 失败、保存命中默认拒绝名单、S11 警示卡出现 | `.warning` |
| 删除失败、接管不可回退点之后的失败 | `.error` |
| 撤销与删库的最终按钮按下 | 重冲击触感 |
| 明文展开、勾选授予条目 | 轻冲击 |

其余一切滚动、切换、加载一律无触感。触感的职责是给「不可逆」和「校验通过」打触觉书签；到处都震等于没有震。

### 3.8 Liquid Glass：iOS 26 的材质与导航（v0.5）

部署目标从 iOS 17 提到 iOS 26。两条原则：系统给的材质不自绘模仿，自绘的浮层用系统玻璃 API，而不是自己画半透明圆角；我们自己画的东西一律是平的——没有渐变、光晕、阴影，没有卡片，没有图标瓦片底色，分层只靠发丝线和留白。

- 系统栏、导航栏、Tab 栏、sheet 的玻璃材质由系统提供，App 不做任何「假玻璃」。
- TabView 用系统浮动玻璃 Tab 栏；同步状态做成 `tabViewBottomAccessory` 的小胶囊（同步中 / 失败 / 已同步三态），不占一整条横幅位——S6 的失败详情仍在列表顶部展开，胶囊点按展开。
- 主按钮 `KeyrefPrimaryButtonStyle`：前景色实心块 + 页面色字，单一填充、中等圆角、无渐变无光晕。创建保险库、确认轮换、接管提交都用它。次级操作 `KeyrefSecondaryButtonStyle`：同形描边。破坏性动作维持 §3.3 的三档确认与红色语义，材质不改变确认层级。
- 系统控件（Toggle / Picker / SecureField / searchable / 导航栏 / Tab 栏 / 底部配件）是 SwiftUI 原样；accent 走 `.tint(KeyrefTheme.tint)`，跟着前景色走，不染彩色。
- 自绘浮层改用 `glassEffect(.regular)` 胶囊：明文展开层的收起与拷贝按钮、扫码页的手电筒按钮、同步状态胶囊。同屏多个玻璃元素包进 `GlassEffectContainer`，避免材质叠加发浑。
- 恢复码分组框与审批页的 argv 原文不是浮层，是实心「明文层」（slab）：浅色下近黑、深色下近白，是整页唯一的暗块，一眼能找到。不套玻璃，也不做半透明。
- 琥珀只作小面积信号：品牌标记里的钥匙、步骤条的当前步、待审批角标的小方点、指引页的步骤号。除此之外整页只有状态色（成功 / 警告 / 危险 / 信息）。
- 列表滚动边缘用 `scrollEdgeEffectStyle(.soft)`，内容从栏下自然穿过；S1 欢迎页背景用 `backgroundExtensionEffect` 承接状态栏与底部。
- §3.6 的无障碍决定不变：玻璃只换材质不换读法；§3.7 的触感表不变。
